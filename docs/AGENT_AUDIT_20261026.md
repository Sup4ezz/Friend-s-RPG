# LORGUS — координированный read-only аудит, раунд 1

Дата: 2026-10-26  
Ветка исходного кода: `main`  
Режим: только чтение исходников и существующей документации. В рамках этого раунда код приложения, production Supabase, Telegram outbox и развёртывание не изменялись.

## Как выполнялась проверка

Проверка разделена на независимые рабочие потоки:
1. Архитектура и релизный процесс.
2. Безопасность серверных RPC и SQL-миграций.
3. Telegram notifier и маршрутизация уведомлений.
4. Сверка найденного с мастер-чеклистом и постановка следующего безопасного шага.

Это статический аудит репозитория и ранее зафиксированных read-only наблюдений. Он не заменяет runtime SQL-тесты и браузерную проверку.

## Краткий вывод

Не начинать с массового рефакторинга и не выкатывать изменения. Сначала устранить противоречия между документированным хостингом и workflow, проверить два точечных security finding в изолированной среде, затем исправлять Telegram-маршрутизацию и провести browser QA.

## Находки

### A1. Деплойный workflow может не совпадать с фактическим хостингом

Файл `.github/workflows/deploy-lorgus.yml` в `main` запускается при push в `main` и вызывает Cloudflare Wrangler `deploy`. При этом в недавних сообщениях владельца указан новый статический адрес Layero, а в `LORGUS_CHECKLIST.md` по-прежнему указан старый Cloudflare Worker как production.

**Вывод:** репозиторий пока не доказывает, что Layero является источником текущего production. Push в `main` может запускать Cloudflare deploy. До выяснения фактического маршрута не менять workflow и не считать Layero/Worker синхронизированными.

**Следующий шаг:** read-only проверить свежие GitHub Actions runs, их commit SHA и фактическую версию на обоих адресах. Если Layero — основной хост, отдельно спроектировать безопасный переход workflow; не отключать старый deploy до подтверждения.

### A2. Currency transfer SECURITY DEFINER не проверяет blacklist/access gate

В документированном production-аудите `public.lorgus_transfer_character_currency_in_chat(...)` отмечена как SECURITY DEFINER RPC без `lorgus_is_access_blocked()`. Ветка `audit/currency-transfer-blacklist-guard` содержит узкую миграцию `supabase/migrations/20261025100000_currency_transfer_blacklist_gate.sql`, которая добавляет gate перед auth-проверкой и сохраняет остальную логику.

Статическая сверка исходника и draft уже описана в `.agent/RP_PRESENCE_AUDIT_20261025.md`; динамические SQL-тесты не выполнены, миграция не в `main` и не применена к production.

**Следующий шаг:** в изолированной тестовой среде проверить обычный перевод, заблокированного пользователя, недостаточный баланс, owner checks и сохранение ACL. Не тестировать переводы или blacklist на живых игроках.

### A3. Telegram outbox: известная причина 35 ошибок, но маршрутизация ответов/упоминаний ещё требует исправления

В мастер-чеклисте зафиксированы 35 недоставленных событий `rp_message` с ошибкой Telegram `Bad Request: message thread not found`. В `main` notifier направляет `rp_message` в admin group `-1003769316441`, topic ID `1`. Ветка `audit/telegram-rp-outbox-thread-fix` удаляет `rp_message` из `deliveredTypes` и DM preference mapping, что соответствует требованию не отправлять уведомление на каждый RP-пост. Эта ветка не развёрнута.

Дополнительная статическая проверка выявила:
- `rp_reply_notification` и `character_mention_notification` направляются в один общий topic ID `1`; отдельная тема упоминаний пока не отражена в маршрутизаторе.
- В `formatEvent()` два `case "rp_reply_notification"`; второй недостижим, поэтому личное уведомление может использовать формат первого случая вместо предназначенного для адресата.
- Для `character_mention_notification` нет отдельного case в `formatEvent()`; сейчас срабатывает общий fallback.
- Отключение `rp_message` подавляет старые события при обработке notifier-ом; это не отправляет их повторно в Telegram. До deploy нужно явно согласовать такое подавление.

**Следующий шаг:** выяснить и подтвердить реальные chat/topic IDs для «АНКЕТЫ», «Предметы», ответов и упоминаний. Затем подготовить отдельный review diff с явной таблицей event type → destination/topic → DM preference и тестами форматирования. Не угадывать topic ID и не посылать тестовые сообщения в production без подтверждения.

### A4. SECURITY DEFINER trigger для клиентских ошибок требует отдельной проверки grants

Миграция `supabase/migrations/20261016103000_lorgus_client_error_telegram.sql` создаёт trigger function `public.lorgus_telegram_client_error_event()` с `SECURITY DEFINER`, но в этом migration-файле нет явного `REVOKE EXECUTE`. В мастер-чеклисте ранее зафиксировано предупреждение Supabase Advisor о лишнем EXECUTE для anon/PUBLIC.

Это потенциальная проблема прав, а не доказательство, что функцию можно вызвать напрямую через RPC. Это trigger function; trigger должен продолжить работать после ограничения grants.

**Следующий шаг:** read-only проверить фактические ACL в production и все места вызова. Затем подготовить отдельный минимальный SQL patch с явным сохранением trigger-поведения и проверить его в тестовой среде. Не применять в production в рамках аудита.

### A5. Админское зависание, медленная работа и Markdown-рендеринг не подтверждены повторным runtime-тестом

В документации сохранены пользовательские симптомы:
- админка зависает на проверке прав/blacklist, хотя отдельный ручной `is_admin()` RPC ранее успешно отвечал;
- после миграции хостинга интерфейс на ПК работает медленно;
- Markdown в «Архив летописца → Легендарные существа» ранее оставался сломанным.

В этом раунде не выполнялась браузерная проверка, и первопричина этих симптомов не установлена.

**Следующий шаг:** после фиксации текущего deploy SHA провести воспроизводимые измерения в браузере: network timings, повторные RPC, тайм-ауты/ретраи, загрузку портретов, этапы запуска админки и конкретный Markdown-раздел. Не отключать проверки доступа ради устранения зависания.
